# Convex Cloud development

Requires Node.js 20.9.0 or newer and pnpm 10.16.0. The selected development
deployment is `formal-giraffe-877` in the `andres-mbouh/shuttle-tracker` project:

- Backend URL: `https://formal-giraffe-877.convex.cloud`
- [Development dashboard](https://dashboard.convex.dev/t/andres-mbouh/shuttle-tracker/formal-giraffe-877)

## Connect this repository

Install dependencies with `pnpm install`. The Convex CLI stores the selected
deployment in the git-ignored `.env.local`:

```dotenv
CONVEX_DEPLOYMENT=dev:formal-giraffe-877
NEXT_PUBLIC_CONVEX_URL=https://formal-giraffe-877.convex.cloud
NEXT_PUBLIC_CONVEX_SITE_URL=https://formal-giraffe-877.convex.site
```

These URLs identify the deployment; they do not authorize backend administration.
CLI access uses your local Convex login. Keep account credentials and deployment
keys out of the repository and out of `NEXT_PUBLIC_` variables.

On an already authenticated machine, link this existing deployment with:

```bash
pnpm exec convex deployment select formal-giraffe-877
```

If authentication is required, run `pnpm exec convex dev`, complete the browser
login, and select the existing project and cloud development deployment. Confirm
the selected deployment before syncing. Do not create a replacement project.

## Run frontend and backend development

Start the Next.js frontend in one terminal:

```bash
pnpm dev
```

Open [http://localhost:3000](http://localhost:3000). View 1 currently uses the
working fixture demo. Live subscriptions will be connected in Feature 7b.

In a second terminal, watch and sync backend changes:

```bash
pnpm convex:dev
```

For one sync that checks types and exits:

```bash
pnpm convex:dev --once
```

Stopping the CLI stops watching local files. The cloud backend keeps running and
retains its data. The frontend continues using fixtures until Feature 7b, and
`pnpm build` does not need Convex credentials or a live backend connection.

## Generated types and checks

Convex functions and schema live in `convex/`. Generated bindings in
`convex/_generated/` belong in git and are regenerated by the CLI. Do not edit
them manually. Regenerate or check backend types with:

```bash
pnpm convex:codegen
pnpm convex:typecheck
```

Run the project checks from the repository root:

```bash
pnpm exec tsc --noEmit
pnpm convex:typecheck
pnpm lint
pnpm test
pnpm build
```

The schema defines all nine domain tables: organizations, users, locations,
shuttles, journeys, route legs, waitlist entries, route-leg comments, and routing
snapshots. Schema validators enforce shapes and reference table types; semantic
checks live in the validation helpers:

- `validation.ts` checks numeric bounds and organization/driver relationships.
- `journeyValidation.ts` checks ordered legs, endpoints, and the assigned shuttle.
  A new Journey/RouteLeg graph has circular references: insert and link its native
  IDs in one mutation, then call `validateJourney` before that mutation completes.
  Let validation errors abort the transaction so incomplete graphs cannot commit.
- `routeDataValidation.ts` checks new active waitlist entries/comments and routing
  snapshots. New rider records must reference the leg's current cycle. These
  checks establish data integrity; identity authorization and pickup eligibility
  still belong to the future mutation handlers.

Waitlists and comments are separate records keyed by route leg and cycle, starting
at 1. Active reads must filter on both values; old-cycle records must not appear
on the reset leg. This storage supports either later deletion or archiving and
does not advance cycles or apply a retention policy itself.

Routing snapshots are intended to hold one latest record per leg. Indexes do not
enforce uniqueness: the seed must reject duplicate source records, and future
writers must enforce membership/snapshot uniqueness within their transactions.

## Reference seed preparation

`seedData.ts` prepares the existing Sunday Service fixtures for import without
database access. It keeps fixture IDs as lookup keys, copies records so later
edits cannot change the demo fixtures, and extracts waitlists/comments into
separate cycle-1 records. The active outbound leg is selected explicitly.
Original statuses and historical timestamps are preserved, including tracking
and routing timestamps; these are sample readings, not fresh shuttle telemetry.

`seedValidation.ts` checks the complete source graph before preparation returns:
unique fixture IDs and memberships, ordered legs, required users/endpoints,
organization ownership, driver assignment, and one valid routing snapshot per
leg. Errors contain fixed codes/field labels, not guest contact details.

Verify this preparation locally with `pnpm test convex/seedData.test.ts`.
Expected totals are 1 organization, 8 users, 2 locations, 1 shuttle, 1 journey,
2 legs, 6 waitlist entries, 2 comments, and 2 routing snapshots.

## Guarded development import

`seed:run` is an internal mutation with empty arguments. It requires both
`ALLOW_DEVELOPMENT_SEED=true` in the backend environment and the runtime
`CONVEX_CLOUD_URL` to match `https://formal-giraffe-877.convex.cloud`.
Setting a variable in Next.js `.env.local` does not enable the backend seed.
The function is disabled by default and has no public client wrapper.

The import allocates native IDs and links the entire graph in one mutation.
It writes `seedRuns` with the key `sunday-service-v1` only after all records
validate. Any failure aborts the transaction with `SEED_IMPORT_FAILED`;
the underlying error and guest records are not logged or returned.

| Result | Meaning |
| --- | --- |
| `disabled` | Backend opt-in is absent/not exactly `true`, or this is another deployment. |
| `seeded` | The full dataset and completion marker were created; the result includes counts. |
| `already_seeded` | A completion marker exists. No records are re-created or modified. |
| `conflict` | A domain table contains data without this completion marker. Nothing was written. |

Each result also contains `seedKey`, never user records. A completed seed stays a
no-op after status edits, cycle changes, or deletion of memberships/comments.
There is no force/reset option. Do not delete the marker or change the key to
reapply fixtures over existing activity.

The marker lookup, all nine empty-table checks, imports, and marker insertion
share the same transaction. This uses Convex's
[atomic transactions and concurrency handling](https://docs.convex.dev/database/advanced/occ).
The in-memory concurrency test serializes calls. The development verification
also launched two CLI seed invocations concurrently against the real backend;
one imported the dataset and the other returned `already_seeded`.

First confirm the Development target in the sync output. Enable, run, and disable
the seed using these explicitly scoped commands. This deployment is already
seeded, so enabled reruns now return `already_seeded`:

```bash
pnpm convex:dev --once
pnpm exec convex env --deployment formal-giraffe-877 set ALLOW_DEVELOPMENT_SEED true
pnpm exec convex run seed:run '{}' --deployment formal-giraffe-877
pnpm exec convex run seed:run '{}' --deployment formal-giraffe-877
pnpm exec convex env --deployment formal-giraffe-877 remove ALLOW_DEVELOPMENT_SEED
```

Keep the backend opt-in disabled after verification, including after a failed run.
The local logic tests can be run without enabling it:
`pnpm test convex/seed.test.ts`.
